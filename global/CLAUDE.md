# Working rules for every project

These come from the `session-kit` repository (`global/CLAUDE.md`). A project's own `CLAUDE.md` adds to them and wins where it says otherwise. The rules marked **(refused)** are enforced by the plugin's guard and no longer depend on being read. The reason behind each rule is in `RATIONALE.md` beside this file in that repository (the link at `~/.claude/CLAUDE.md`, or the `@` line that imports this file, names the directory), under the same heading: read it when a rule looks arbitrary or you are about to argue with one.

The plugin's commands, `session-tells`, `session-codeintel`, `session-intent`, `session-transcripts`, `session-suppressions`, `session-rulebook` and `session-docs`, are on the Bash tool's PATH while it is enabled. The language-server shims are put on PATH once per machine by `plugins/session-kit/codeintel/shims/install.sh`, run from the marketplace's clone at `~/.claude/plugins/marketplaces/galileo-kit/`: it links to the directory it runs from, and the plugin's own copy moves with every version.

## How to work

- **Say what you are about to do, then do it.** Restate a multi-part ask and its deliverables before exploring. Ask clarifying questions up front, before the work starts. Otherwise work autonomously and record the assumptions you made, so they can be reviewed.
- **Be critical.** Question every design decision, the owner's included, and offer the better alternative when there is one.
- **No abstraction before its second use.** No Protocol layer, plugin system or extension point until a second implementation exists. Use third-party types directly.
- **When a signature changes, the typechecker finds the callers.** Make the change, run the typechecker over everything that could call it, and work through its error list: that list is the ground truth. A language server's find-references maps the callers before the change. The typechecker says what broke after it. For a change the types cannot see (a string key, a reflective call, a config file), search the text and read every hit.
- **A mechanical sweep goes through a parser.** A change repeated over about ten sites or more (a rename, a call that went async, a moved import) is made with a tool that matches syntax, such as `ast-grep`, and never with a regex. Start from a tested rule (`session-codeintel recipes list` ships some), and try it on a planted case before the tree. Below ten sites, edit each by hand and let the typechecker check them. Finding things stays grep and reading.
- **Surface unrelated failures immediately.** A failure that is not yours is never fixed without a word and never called flaky. One line saying what failed and a proposed next step, usually a follow-up commit.
- **A fix that has not worked after two tries stops and shows evidence.** State what was tried and what happened, and let the owner or the next reader decide, instead of looping a third and fourth time blind. A mismatch between layers is fixed in the layer that holds it.
- **You own what you grew.** A gate your change trips is yours to answer, in your own commit, even when that means a structural edit to a shared file. A file you push past a length cap is split by you, at the seam it shows.
- **A deliverable is a file.** A report, plan, diagram or summary that was asked for is written as a local file and answered with its path. Never publish a Claude Code Artifact, and never offer one. **(refused)**
- **A new document gets its line in the index in the commit that adds it.** `session-docs check` fails on a document under `docs/` that the project's `CLAUDE.md` does not name, by its path or its directory's, and on a line naming one that is gone.
- **A file you touch leaves with fewer prose tells.** Write none in what you add, and remove those already in the comments and prose of every file you edit, whether or not they bear on the change. Remove a tell by rewriting the sentence: a dash swapped for a comma is the same sentence. A comment that tells history (an issue number, a date, `used to`) is deleted. Quoted text and a string a test asserts on stay as they are. The plugin's hook lists the tells an edit wrote, and `session-tells show <file>` lists a file's.
- **A temporary file is scoped to whoever wrote it.** Sessions on one machine run at the same time, so a fixed name under `/tmp` is last-writer-wins. Name it after the session or the worktree, or make it with `mktemp`.
- **What is kept gets an entry in the project's intent.** A rule, a design choice, a plan of several phases or a decision a later session relies on is written under `docs/intent/` as a goal, an objective, a constraint or an action, by the process in `goals-objectives-actions.md` beside this file: goals in the owner's words, objectives the owner approves, actions a session decides and the owner validates, each naming what it comes from. A one-off task writes nothing. `session-intent next <level>` gives a new entry its id, claimed under a lock so two sessions never pick the same one. `session-intent index` regenerates `docs/intent/INDEX.md` after an entry changes, and `session-intent check` is the gate on the record.
- **An id carries its name.** An id of any kind the project uses (an intent entry, an issue, a ticket, a planned chunk of work) is written with its name (`A20`, one module per concern), at its first mention in a reply and in each section of a document the owner decides from: a plan's next steps, open questions, a handoff, a briefing. An id alone means nothing to the owner once they number in the dozens. For the intent the names are a call away: `session-intent names` prints every entry's, or those of the ids given.

## Sessions

- **One task per context.** A prompt unrelated to the task in `CLAUDE.local.md` is named as such before anything starts on it. With the plugin's `chain` option on, call its `new_task` tool and end the turn: the band offers the handoff and a clear, or to keep going here, and sends the prompt again after. Otherwise say in one line that it is a new task and propose the handoff and `/clear` before starting.
- **Ask for a compaction at a clear point.** Between two phases of work (the build finished and the checks not yet run, a review requested, a question answered and its work not started), commit, write `CLAUDE.local.md` (`/session-kit:handoff`) and end the turn asking to compact. Under 150,000 tokens of context, skip the ask. The plugin's hook warns from 250,000 tokens, every 25k, firmer from 500,000.
- **After a compaction or a clear, read again in full the documents the work rests on**, before the next step: the ones `CLAUDE.local.md` lists, and any the owner named in the session. A summary keeps a document's conclusions and loses the detail a decision turns on, such as an option's condition or a failure path.
- **Memory holds what crosses conversations: preferences and feedback.** A project's state lives in its files (its `CLAUDE.md`, its decisions and plans, `CLAUDE.local.md`), where the next session and the next person can read and check it. A note you are asked to make goes where it belongs: a rule of engagement in the project's `CLAUDE.md`, deferred work in its plan, a preference in memory.

## Git

- **Commit proactively**, whenever a logical unit is complete. Never leave finished work in the working tree.
- **Never deliver red.** What is handed back as done (a reply saying it is finished, a merge, a push) is green on the checks its author runs: the gates and the tests the change reaches. A project may let an integration branch go red after a merge when its own rules name who proves the union. The exception is a fix that has failed twice, which is delivered red with its evidence.
- **Work only in your own checkout and on your own branch.** Run every command from it. Never merge, rebase, cherry-pick or pull another branch into yours, and never commit to a branch that is not yours, unless asked. The stash is shared by every worktree of a repository: never a bare `git stash` or `git stash pop`. Use a WIP commit, or `git stash push -m <tag>` and apply by SHA. **(refused)**
- **Refused outright:** `git commit --no-verify`, `git reset --hard`, amending a commit already on a remote, and a force-push (`--force-with-lease` is fine). **(refused)**
- **Publishing is the owner's.** Never push, open a pull request or publish anything unless asked.

## Gates and tests

- **Quality gates are zero warnings.** A warning is a failure, and the bar is not lowered to pass it.
- **The rulebook has a word budget.** What every turn loads (the global rules, the project's `CLAUDE.md` with its imports, its `.claude/rules/`, and `CLAUDE.local.md`) and the skills are counted apart by `session-rulebook`, against `rulebook` in `.claude/claude-kit.json`, and a group over its budget fails the gate. A rule that takes the rulebook over removes another.
- **Suppressions and type escapes need the owner's approval**: `noqa`, `type: ignore`, `pyright: ignore`, `@ts-ignore`, `@ts-expect-error`, `Any`, a cast out of `object` or `unknown`, a rule relaxed in config. Surface the trade-off, and the owner picks refactor, suppress or re-scope. An approved one is a numbered row in the project's decisions file (`docs/decisions.md`), cited beside the marker, and `session-suppressions check` holds the two together. The plugin's hook names the markers an edit wrote. Deleting one needs no approval.
- **Test output goes to a file**, which is then searched. Never pipe it inline to `grep`, `head` or `tail` (**refused**), never stop at the first failure with `-x` (**refused**), and never wrap a Bash call in shell `timeout`, since the tool has its own (**refused**). The plugin also keeps the last test run's whole output in `<tempdir>/claude-kit-last-test-<session id>.log` and names that file when a run fails.
- **A slow test is a smell, and a danger until it is acknowledged.** Give every test a timeout of a few seconds. A test that needs more is a finding, kept only when the owner accepts it and its reason is written beside it (a marker, a tier of its own). A run that outgrows the tool's timeout is the same finding: raising the cap to fit it removes the signal.
- **Blind tests are scaffolding.** Before the code, write the tests that say what it must do, from the behaviour asked for and never from the code (or hand them to a sub-agent that has not seen it). They prove the change while it is built. Before the work is called done, delete them, except three kinds, each kept at a boundary: a defect's regression test, a test of what the project promises other systems, and a test of a rule whose failure is silent and costly (who may see or do what, money, data that can be lost, secrets). A project may name more.
- **A defect fix lands with a regression test that failed before it.** A weak test's fix is the strengthened assertion.
- **Each test proves a sentence nothing else proves.** Before writing one, name the sentence it proves and check that nothing already proves it: the typechecker, an existing test, a gate. Prefer one file with a few pointed cases over a file per module.
- **Done means it was run.** Passing tests prove the code does what their author expected, and nothing about whether the feature works. Before saying a feature is done, drive it the way its user would: the screen, the real call, a real model where it needs one. Say which scenarios ran, which did not, and why.
